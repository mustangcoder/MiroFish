# 已上传文件库与跨推演复用设计

## 背景

当前新建推演时，前端只能提交浏览器中临时选择的文件。后端会把文件直接保存到新项目的 `files/` 目录，文件生命周期与项目绑定，因此既不能查看和管理历史上传文件，也不能在新的推演任务中复用它们。

本需求将上传文件提升为独立资源：用户可以管理已上传文件，并在创建新推演任务时引用一个或多个已有文件。

## 目标

- 提供全局文件库，支持列表、搜索、上传、重命名、下载和删除。
- 展示每个文件当前被哪些项目引用。
- 创建新推演时可多选文件库中的文件，也可同时上传本地新文件。
- 同一文件可被多个项目引用，不产生项目级重复副本。
- 文件仍被项目引用时禁止删除，并返回引用项目供用户处理。
- 自动兼容现有项目中的历史上传文件。

## 非目标

- 不提供文件内容在线编辑或预览。
- 不提供文件夹、标签、版本历史和权限系统。
- 不允许修改已创建项目所引用的文件集合。
- 首版不按内容哈希自动合并重复上传；哈希只用于完整性与后续扩展。

## 方案选择

采用“独立文件库 + 项目引用关系”。文件物理存储在 `uploads/library/`，元数据及项目引用关系存储在统一 SQLite 数据库。

没有采用“引用时复制到项目目录”，因为它会造成重复占用并使重命名、引用统计和删除语义变得含糊。也没有直接索引旧项目目录，因为文件路径仍受原项目生命周期影响，删除项目后容易产生悬空引用。

## 数据模型

### `uploaded_files`

- `file_id`：稳定资源 ID，格式为 `file_<随机值>`。
- `display_name`：用户可修改的展示名称，必须保留受支持的扩展名。
- `stored_filename`：服务端生成的不可变存储文件名。
- `extension`：规范化的小写扩展名。
- `size`：文件字节数。
- `sha256`：内容哈希。
- `created_at`、`updated_at`：ISO 时间。
- `legacy_source`：旧项目迁移来源标识，可为空；用于保证迁移幂等。

### `project_files`

- `project_id`。
- `file_id`。
- `position`：项目语料拼接顺序。
- 联合主键为 `(project_id, file_id)`，并对 `file_id` 建索引。

项目的 `project.json` 继续保留 `files` 字段作为兼容快照，但每项增加 `file_id`。权威引用关系以 SQLite 为准。

## 存储与安全

- 物理文件统一存放在 `Config.UPLOAD_FOLDER/library/`。
- 存储文件名由服务端生成，不使用用户输入拼接路径。
- 上传与重命名均校验扩展名，仅支持现有配置允许的 PDF、Markdown 和文本文件。
- 下载响应使用展示名称，同时由服务端解析固定库目录下的存储路径，防止路径穿越。
- 上传继续遵守 Flask 的 50MB 请求上限。

## 后端组件

新增 `UploadedFileStore`，集中负责：

- 初始化表结构和库目录。
- 保存文件、计算哈希和写入元数据。
- 查询文件列表及引用项目。
- 重命名文件。
- 建立和解除项目引用。
- 在无引用时删除数据库记录与物理文件。
- 执行旧项目文件的幂等迁移。

项目创建流程调整为：

1. 校验 `simulation_requirement`。
2. 解析表单中的 `file_ids`，校验所有文件存在。
3. 将本次新上传文件写入全局文件库。
4. 合并已有文件与新文件，并要求结果非空。
5. 创建项目，建立 `project_files` 引用并写入兼容快照。
6. 按选择顺序解析文件并生成项目语料、本体和后续图谱。
7. 若项目创建或解析失败，删除已创建项目及其引用；新上传的文件仍保留在文件库，避免用户重新上传。

删除项目时，在同一个 SQLite 写事务中先把项目目录原子改名为同级 tombstone，使项目立即不可见，再解除 `project_files` 引用并提交；引用事务失败则回滚并恢复原目录。提交后的 tombstone 清理通过持久删除 operation 幂等重试，不得把已经解除引用的项目恢复为活项目。删除文件时若存在引用，返回 HTTP 409 和引用项目摘要；无引用时才删除记录及物理文件。

## API 设计

新增 `/api/files` 接口组：

- `GET /api/files?query=&limit=&offset=`：分页查询文件，并返回 `reference_count`。
- `POST /api/files`：上传一个或多个文件，返回文件元数据。
- `PATCH /api/files/<file_id>`：修改展示名称。
- `GET /api/files/<file_id>/download`：下载文件。
- `GET /api/files/<file_id>/references`：查询引用项目。
- `DELETE /api/files/<file_id>`：无引用时删除；有引用时返回 409。

`POST /api/graph/ontology/generate` 保持 `multipart/form-data`，新增可重复的 `file_ids` 字段，并继续接受可重复的 `files` 字段。两种来源可混用，合并后至少包含一个有效文件。

ontology 创建在保存上传或创建项目之前，使用文件库公开校验器验证整批上传名称和扩展名；任一文件非法时整批返回 HTTP 400，不保存本次新文件。已有 `file_id` 必须处于可引用状态；不存在时返回 404，删除中或无法恢复的删除失败状态返回 409。

所有接口沿用项目现有的 `{ success, data, error }` 响应格式。

## 旧数据迁移

文件库首次读取或写入前执行共享、轻量、幂等且失败可重试的迁移门禁。files API、ontology 创建和项目删除共同使用该门禁：

1. 遍历现有项目元数据。
2. 对没有 `file_id` 的旧文件，根据项目 ID 与保存文件名生成稳定 `legacy_source`。
3. 将物理文件复制到全局库并写入 `uploaded_files`。
4. 建立 `project_files` 引用并回写项目的兼容快照。
5. 保留旧项目目录中的原文件，不改变历史项目当前行为。

迁移单个文件失败时记录日志并继续其他文件；对应项目仍可沿用旧路径，不会因为局部迁移失败而无法读取历史记录。

删除项目还会校验该项目每份旧源都已获得文件库记录和项目引用；迁移异常、跳过或来源无法唯一证明时阻止删除，避免销毁尚未迁移的唯一副本。迁移内部读取和回写 `ProjectManager` 时使用递归门禁，不能再次进入项目删除。

## 前端交互

### 首页创建推演

- 上传区增加“本地上传”和“从文件库选择”两个入口。
- 已选择列表统一展示本地文件和库文件，可逐项移除。
- 本地选择或拖放会先校验整个批次；存在非法名称或扩展名时显示本地化错误并拒绝整批，不静默过滤。
- 提交时把本地文件写入 `files`，把已有文件 ID 写入 `file_ids`。
- 只要推演需求非空且至少选择一个文件即可启动。

### 文件管理页

- 导航栏增加“文件管理”。
- 表格展示名称、类型、大小、上传时间和引用数。
- 支持搜索、上传、重命名、下载、查看引用和删除。
- 引用数大于零时删除操作仍可点击，但会展示引用项目并说明必须先删除相关项目；后端 409 是最终保护。

新增中英文文案，沿用现有页面视觉风格，不引入新的 UI 组件库。

## 并发与一致性

- 表结构初始化和旧数据迁移使用进程内锁，数据库写入使用事务。
- 建立项目引用时验证文件记录仍存在。
- 删除文件时在同一写事务内再次检查引用数并删除记录，避免检查与删除之间的竞态。
- 文件物理删除失败但原路径恢复成功时取消删除 operation，使文件重新可引用；原路径无法恢复时保留 operation，并从可复用列表排除。后续初始化会幂等重试未完成删除。
- 项目删除持有同一 SQLite 写锁完成“目录隐藏 + 引用解除”，因此并发文件删除只能看到“可见且有引用”或“不可见且无引用”两种稳定状态。

## 测试与验收

后端测试覆盖：

- 上传、列表、搜索、重命名、下载与无引用删除。
- 不支持扩展名、空名称、路径型名称和不存在文件 ID。
- 一个文件被多个项目引用。
- 有引用文件删除返回 409，并包含引用项目。
- 删除项目后引用解除，文件可继续被其他项目复用。
- `file_ids`、新上传文件及二者混合创建项目。
- 旧项目文件迁移的成功、重复执行和局部缺失场景。
- 未访问文件 API 时直接删除旧项目仍会先迁移；迁移跳过会阻止删除。
- 项目 tombstone 清理失败可重试、引用事务失败恢复目录，以及并发文件删除窗口。
- 合法与非法文件混合上传时原子 400；删除失败状态不会进入可复用选择或在创建项目后退化为 500。

前端契约测试或静态断言覆盖新路由、API 调用和表单字段；执行完整后端测试，并以 `npm run build` 验证前端构建。

验收标准：用户上传过的文件刷新页面后仍可见；可直接选择它创建新的推演；同一文件能被多个项目使用；被引用文件无法删除；解除全部引用后可成功删除。
